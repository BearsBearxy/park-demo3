# 公摊池入口覆盖度调研（重做版）

> 2026-08-29。**这份是对 `2026-08-29-phase3-pool-opening-design.md` 那次调研的重做**，
> 因为原口径错了：当时只查了「新建池时能选几种方法」，没查「**库里已有的池能不能原样存回去**」。
> 后者才是用户实际会撞上的，也是「现有入口是否覆盖所有公摊情况」的直接答案。
>
> 触发点：用户打开「一期 招商中心·净电」的编辑抽屉，底部红字 `整笔归户规则受益人必须恰好一户`，
> 存不下去。我当时答「配置是对的，弹窗表达不了，别动它」——**那正是「必须改代码」的实例，
> 应判为不合格，我却当成了实现细节。**

## 结论

**不符合交付标准。** 98 个池里：

| 类别 | 数量 | 后果 |
|---|---|---|
| **一个字不改、点保存直接被拒** | **15** | 用户在界面上无法维护这些池 |
| **存得下，但存回去的东西和原来不等价** | **8** | 池名被静默重写，其中 7 个与同栋另一池撞成同名 |
| **可能被静默改写 `fee_key`** | **40** | 载入竞态，无报错 |
| 原样往返完全等价 | 35 | — |

三个类别互不重叠的部分之外，第三类与前两类有交集；「完全等价」的真实数量比原判定书说的 75 个少得多。

方法：对每个池设想「打开抽屉 → 一个字不改 → 点保存并重新生成」，问两件事——
**(a) 会不会被拒？(b) 存回去的东西和原来等价吗？** 第二问是原调研整个漏掉的维度。

## 一、15 个存不回去的池

### 根因 ①：`@Pattern` 值域漏了库里正式在用的两种 method（5 个池）

`backend/.../dto/AllocRuleReq.java:12`

```java
@Pattern(regexp = "direct|area|floor|loss|none|ref") String method
```

值域里**没有 `carrier` 和 `manual`**，而这两种库里都在用：

| 池 | method | 现象 |
|---|---|---|
| 17 二期 五车间·广告字灯(火炬园) | `carrier` | 抽屉里 carrier 档**会渲染**（`PoolLedgerView.vue:512-514` 的通用兜底 `[...base, cur]` 把当前值补进单选组），所以屏上看着正常，点保存必 400。改成别的 method 就再也切不回来——**单向门**。该池还带 `std_kind=qty_over_base` + `base_key=area_base`，被迫改 method 会让整套算式失真 |
| 92 一期 A座·一楼·联塑精铟 | `manual` | 抽屉连单选组都不渲染（`:1143` 只出一行灰字「人工指定(无电表)——分摊方式不在此改」），`form.method` 恒为 `'manual'` 原样回传 → 400 |
| 93 / 94 / 95 一期 C座·一楼西侧·公共用电/杨道扬、卢志华、诺玲 | `manual` | 同 92。93 是 0 表 0 受益人 0 参数，整池只剩名字和定位，抽屉里除了备注什么都能改，却连备注都存不下去 |

### 根因 ②：`direct` 必须恰一户，没给「整笔挂亏池」开例外（10 个池）

`backend/.../service/AllocService.java:621-622`

```java
if ("direct".equals(req.method()) && (req.members() == null || req.members().size() != 1))
    throw new BizException(BAD_REQUEST, "整笔归户规则受益人必须恰好一户");
```

10 个 `direct` + 0 受益人的池全军覆没。**其中 5 个是 `fee_key=park_loss_pool`（整笔挂亏，按语义本就不该有受益人）**：

| 池 | fee_key | 备注 |
|---|---|---|
| **23 一期 招商中心·净电** | `park_loss_pool` | 全库最复杂的池：7 条绑表（2 正 5 负，3 块负表已 `retired_ym=2023-10`）、两条 `extra_qty` 参数（−1470@2023-12 `mode=from`、−670@2024-02 `mode=month`）。这些抽屉都能原样回送，**唯独卡在受益人这一条** |
| 96 / 97 / 98 / 99 | `park_loss_pool` | A座 地下车库东侧照明 / 西侧照明 / 大堂 / 生活加压泵。**双重不等价**：即便补一户存下去，`fee_name` 列是 NULL，池名会被重算成「一期 A座·负一层」「一期 A座·一楼」——描述整段丢掉，96/97/99 三池撞成同名 |
| 30 / 31 | `share_elec_floor` | 招商中心 四楼 公共用电 / 空调外机。有表有钱没人分，绑的 meter 221/222 已 2023-10 退役 |
| 56 / 85 / 86 | `share_elec_floor` | C座四楼东侧 / F座四楼东侧 / F座四楼西侧 公共用电，各绑 1 块表 |

## 二、8 个存得下但会被改名

`AllocService.apply()`（`AllocService.java:634-639`）保存时按**定位四项**重算池名。而一期的历史数据把「东侧/西侧」写在了 `name` 字符串里、**没进 `side` 列**（全库只有 51/52 两个池真用了 `side` 列）。抽屉的侧向框读 `side` 列读到空、原样回传空，方位就从名字里蒸发。

| 池 | 现名 | 保存后 | 撞谁 |
|---|---|---|---|
| 59 / 60 | 一期 C座·天面**东侧**·货梯 / **西侧** | 一期 C座·天面·货梯 | 两池同名 |
| 69 / 70 | 一期 D座·天面**东侧**·货梯 / **西侧** | 一期 D座·天面·货梯 | 两池同名 |
| 78 / 79 | 一期 E座·天面**东侧**·货梯 / **西侧** | 一期 E座·天面·货梯 | 两池同名 |
| **88** | 一期 F座·天面**东侧**·货梯 | 一期 F座·天面·货梯 | **与既有的 89 逐字同名**——89 看上去已经被这条路径改过一次了 |
| 25 | 一期园区·路灯 | 一期园区·**一楼**·路灯 | 方向相反：凭空多出一截楼层（`building_id` 为 NULL 却填了 `floor_label='一楼'`） |

`alloc_rule.name` **无唯一键、无校验**，撞名不报错。

> ⚠ 一处对用户有利的澄清：改名**不是保存后才发现**。抽屉标题（`:1054`）就是
> `'编辑池 · ' + formAutoName`，池 59 在表格里叫「天面东侧·货梯」，抽屉标题从第一眼
> 就写「编辑池 · 一期 C座·天面·货梯」——是预告过的。

## 三、40 个池可能被静默改写 `fee_key`（对抗复查补出的失败模式）

`PoolLedgerView.vue:582`

```js
feeKey: rule?.feeKey ?? 'share_elec_floor'
```

`rule` 取自 `ruleById`，而 `ruleById` 只由 `onMounted` 里 fire-and-forget 的
`loadRules().catch(()=>{})`（`:203`）填充。`rulesFailed`（`:175`）只挡「请求被拒」，
**没有「还在飞」的守卫**，保存按钮是 `:disabled="saving || rulesFailed"`（`:1280`）。

在 `/alloc/rules` 未返回的窗口里打开任一池抽屉并保存，`fee_key` 被静默改写成
`share_elec_floor`。影响 `fee_key` 非 `share_elec_floor` 的 **40 个池**：
`share_elec_elevator` 17、`share_elec_fire` 9、`share_elec_light` 6、`park_loss_pool` 5、`share_green_water` 3。

## 四、两条与「等价」有关的补充

- **保存不是无副作用的空操作。** `submitPool:779-786` 只要 `generated` 为真就
  `await allocApi.generate(ym)`，重写当月 `alloc_pool_result` / `alloc_pool_meter_result` 快照。
- **受益人的 `acct_month` 结构上送不回去（潜在，当前库无影响）。** 抽屉把逐行的 `m.src`
  压成池级布尔 `monthOnly`（`:589`）再压成单个 `memberMonth`（`:766`），后端给**所有**
  受益人盖同一个月份戳。同时有默认行和月行的池，存回去会变成「默认行留着 + 月行复制一份」。
  当前 `alloc_rule_member` 251 行 `acct_month` 全是 `''`，暂不发作。

## 五、查过但确认无雷（列出来是因为它们最像陷阱）

- `ds/Select.vue` 是完全受控组件，挂载时**绝不**回写 `modelValue`——库里的值不在 options 里
  只会让触发器显示占位文案，不会静默清空。`stdKind` / `baseKey` / `floorLabel` / `links[].ruleId` 都不会丢
- `bindsByRule` 用 `selectList(null)` 全量取，**不按 `retired_ym` 过滤**，退役表照样原样回送
- 绑表 `sign`（全库 8 条 `−1`，分布在 rule 14/16/20/23）、权重（125 行 / 17 池 / 73 租户，含 7 行 0.000 与 2 行负值）、
  入向折入链、`std_kind`/`base_key` 全部能原样回送
- 数据层无雷：orphan 绑表/受益人/link 源各 0；`(rule,tenant)`、`(rule,meter)` 无重复；
  `name` 最长 <55 字符，`poolName` 的 64 截断从不触发
- `validateRule` 的另一条分支（`:612-620`，area/floor 必须有正分母）一个池都没拒到

整条路先过 URL 门 `param-policy:edit`（`PermissionRegistry.java:72-73`）。**没这权限的账号
98 个池一律 403**，与池本身无关。

### 引擎不受影响（经代码核实，非仅凭原理）

`AllocService.poolSegQty`（`:1660`）对每条 `alloc_rule_meter` 绑定取 `MeterReading`、
用 `MeterService.usage(prev, curr, factorSnap)` 现算再乘 `sign` 求和，净额池另并入 `alloc_cfg` 的 `extra_qty`。
**全程不读工作簿任何单元格**，更不存在「一期园区电」的行号。入库的账册字段
`book_key='招商中心电1'`、`book_row=8` 都是稳态值（`book_row` 指「公共电分摊明细」的行，12 个月恒为 8）。

两点实务提醒：

1. 引擎的招商中心绑定是照 **2024-02** 标定的，而 2024-02 恰好行号正确、基准没被污染——
   **这是运气不是设计保证**。今后若改用 2023-10/11 做标定基准就会把错值固化
2. 2023-10/11 做引擎↔账册对账时必然出现 1033.79 / 852.23 的差，
   **方向是账册错、引擎对**，别反向迁就引擎
