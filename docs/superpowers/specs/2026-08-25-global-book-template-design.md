# 账册模板全局化：一条链 + 每司版本指针

> 2026-08-25 拍板。取代 BOOK-WORKBENCH-SPEC §2「每司一册一链」。
> 附表10（s10）屏不在本次范围内，其「一册一链」维持原样。

## 1. 为什么改

台账屏现在是**每司一册、每册一条独立版本链**。6 家记账公司 = 6 条链，改一个列名要进 6 次面板。
更糟的是链之间会**静默分叉**：本地实测 6 册已经长成 3 个变体，而其中 4 家公司一行台账数据都没有——
分叉的不是业务需求，是没人维护的出厂默认值。

同时又不能一刀切成"全局唯一版本"：真在用的两家（创显、B2）确实处在不同的演进阶段，
强制拉齐等于替业务做主。

**结论**：模板定义全局唯一（一条链），但**每家公司自己决定停在哪一版**。

## 2. 现状事实（迁移的依据）

三个变体经程序化比对，是**严格包含关系**：

```
B2 相对四司版的改动数 : 3
创显 相对四司版的改动数: 7
B2 的改动是否全部包含在创显的改动里?  True
B2 独有、创显没有的改动:  (空)
```

| 变体 | 内容 | 使用者 | 台账数据 |
|---|---|---|---|
| 四司版 | 出厂默认：商铺与宿舍**合并**成一列 | 帮管好·一泽·积前·创燊高 | 无 |
| B2 版 | 四司版 + **租金拆开**（商铺租金 / 宿舍区租金） | B2 | 有 |
| 创显版 | B2 版 + **维护费也拆开** + 2 个导入别名 + 自定义列「税费」 | 创显 | 有（税费 62 行 / 16,433.87） |

所以三者可以原样落成一条线性链的 v1 / v2 / v3，**零丢失、零取舍**。

## 3. 核心规则

### R1 一条链
台账屏的所有模板版本挂在**同一条链**上，版本号全局递增，只追加不改写。

### R2 每司一个指针
每家公司持有一个 `current_version_id`，指向链上任意一版。这是该公司台账的**列定义与导入词典的唯一来源**。

### R3 只能在链尾编辑
新版本只能从**链尾**长出。公司不在链尾时，模板面板的编辑门关闭，提示「先升到 vN 才能改」。

理由：允许从非链尾分叉，链就不再是一条线，"全局唯一模板"当场失效——退回改造前的处境，只是分叉藏进了版本号里更难发现。

### R4 编辑只带走链尾上的公司
在链尾保存出 vN+1 后：**原本就在链尾的公司**指针跟到 vN+1；落后的公司**原地不动**。
这是"不强制使用"的落点。

### R5 升级不强制，入口在模板面板内
工具条上的「账册模板」按钮两态常驻（位置固定，遵守 LAYOUT-STABILITY §2 优先级 1），
有新版时按钮加角标。面板顶部一行状态：

```
当前 v2 · 最新 v4                    [升到 v4]
```

在链尾时显示「当前 v4 · 已是最新」，无按钮，**不留空洞不挪版**。
升级按钮旁列出待升各版的 `note`（改了什么），点按钮才切。

不做成工具条上忽隐忽现的按钮——那正是 LAYOUT-STABILITY §6 禁的事。
也不进 §6 的告警抽屉——抽屉是给「不处理会出错」的事用的，模板有新版是可选升级，
混进去会稀释告警的严肃性。

### R6 切版本受归档守卫拦截
切到**缺列**的版本时，若该公司在那些自定义列名下**已有数据**，拒绝（409）并指名列与行数。

理由：应收合计的口径是 `ExtraFees.sum(extra_fees) + 21 个物理列`（`LedgerService.recalc`），
**它不看模板**。列从模板里消失但值还在，合计里就多一笔看不见的钱，屏上永远对不上明细。

这条不是新发明——`BookService.assertNoDataLossOnCustomRemoval` 已经在模板编辑与回滚路径上做同样的事
（注释原话：「口袋残值变成合计里看不见的钱」）。本次是把同一个守卫接到切版本路径上。

### R7 回滚退化为切指针
旧的「回滚 = 复制历史版为新版本」在全局链下会污染所有人：一家公司想退回，却给全链造了个新版本。

新语义：
- **本公司要退回旧版** → 就是 R2 的切指针（`adopt`），不造新版本
- **链尾改错了要撤销** → 在链尾再编一版盖回去，历史不删

### R8 跨版跳跃允许
B2 在 v2、链尾在 v5，可以直接指到 v5，不必逐版爬。

### R9 权限
链尾编辑与切版本**同走第 16 权限点 `book-template:edit`**——切版本改变了该公司的列结构与导入词典，是写操作。
查看链与历史版本定义（GET）维持全员可读。

## 4. 数据模型

```
ledger_book
  ├─ 新增一行「台账通用模板」(screen='ledger', company_id=NULL)   ← 链的宿主
  └─ 6 家公司的行保留：company_id / 册名 / current_version_id     ← current_version_id 即版本指针

book_template_version
  └─ 台账的所有版本 book_id 一律指向宿主行 = 一条链
```

**s10 屏恒等变换**：4 个期区册各自 `book_id` = 自己，一册一链，代码路径不变。

`uk_book_company (screen, company_id)` 在 MySQL 下多个 NULL 互不冲突，
不会阻止宿主行插入；宿主行唯一性由幂等的种子逻辑保证，不加约束（YAGNI）。

## 5. 迁移

### 为什么不用纯 SQL
归并需要判断 JSON 模板定义之间的**包含关系**，SQL 做不了。
且生产库的分叉情况未必与本地一致，纯 SQL 迁移遇到意外形态只会写坏数据。

### 做法
- **V110（SQL）**：只建结构——插入宿主行；不动任何既有数据。
- **归并逻辑放在 `BookService` 的启动幂等方法**里（沿用现有 `seedMissing()` 模式），
  因为它需要 Java 侧的 JSON 比对。

### 归并算法
1. 取 6 家公司**现行版**的 definition，按内容去重
2. 对每个去重后的 definition，计算相对出厂标准模板的**改动集合**
3. 按改动集合的**包含关系**排成偏序；转成线性链 v1..vN
4. **若存在互不包含的变体 → 迁移失败并报出是哪几家**，人工先归并再启动
   （fail-fast，与本仓 `${VAR:?}` 一类 fail-closed 风格一致；本地已验证是严格包含链，会通过）
5. 各司指针指向自己那一版
6. 删除旧的每司版本行

### 备份
删除前把 `book_template_version` 与 `ledger_book` 整表导出到
`docs/data-fix/book_template_before_global_20260825.sql`，
沿用 `monthly_ledger_before_prevfix_20260825.sql` 的既有做法。
唯一真正退场的是创显被自己 v2 取代的那个历史 v1。

## 6. 接口变更

| 端点 | 变化 |
|---|---|
| `GET /api/books?screen=ledger` | 仍返回各司册（definition = 各自 pinned 版本）。**新增字段** `latestVer`。宿主行不出现在列表里 |
| `PUT /api/books/{id}/template` | id 传公司册 id。**新增前置校验**：该公司不在链尾 → 409「你在 v2，最新是 v4，请先升级再改」。保存后按 R4 只带走链尾上的公司 |
| `GET /api/books/{id}/template/versions` | 返回**全局链**；`current` 标记为该公司的 pin |
| `GET /api/books/{id}/template/versions/{ver}` | 不变 |
| ~~`POST /api/books/{id}/template/rollback`~~ → `POST /api/books/{id}/template/adopt` | **改名并改语义**（R7）：切本公司指针到 `{ver}`，不造新版本，走 R6 守卫。旧名不保留——一个不再回滚的 `rollback` 是留给凌晨三点的陷阱 |

新增 DTO 字段：`BookDTO` 增 `latestVer`（int）。
「有没有新版」由前端用 `ver < latestVer` 现算，不再传第二个布尔字段。

## 7. 守卫改造

`assertNoDataLossOnCustomRemoval` 现在用 `b.getCompanyId()` 限定数据检查范围，需分两种情形：

- **链尾编辑**（宿主行，`companyId == null`）→ 检查**所有公司**的 `monthly_ledger`，
  任一家在待删列名下有数据即拒绝。模板是全局的，删列影响所有人。
- **切版本**（公司册行）→ 检查**该公司自己**的数据。现有逻辑正好，不改。

## 8. 测试

**后端**
- 链尾编辑 → 新版本入链；在链尾的公司指针跟进，落后的公司**原地不动**（R4）
- 非链尾公司调 `PUT template` → 409（R3）
- `adopt` 升级：跨版跳跃到链尾（R8）
- `adopt` 降级到缺列版本、该公司**有数据** → 409（R6）
- `adopt` 降级到缺列版本、该公司**无数据** → 放行
- 链尾编辑删除某自定义列，**另一家公司**在该列有数据 → 409（§7 跨公司检查）
- `customIdsByCompany` 取该公司 pinned 版本的自定义列（导入词典跟着指针走）
- **s10 回归**：4 个期区册的编辑/版本/回滚行为逐条不变
- **迁移**：归并后 6 家公司的 definition 与迁移前**逐字节相同**；互不包含的构造用例 → 迁移失败并指名

**前端**
- `templateEditor.spec.ts`：落后态渲染「当前 vN · 最新 vM」+ 升级按钮；链尾态渲染「已是最新」且**无按钮但不塌陷**
- 落后态编辑门置灰
- 无新版/有新版切换时工具条**不挪版**（沿用 `noInteractionLayoutShift.spec.ts` 的门禁形状）

## 9. 明确不在本次范围

- **s10 屏**：4 个期区册维持一册一链
- **`hidden` 字段与 recalc 的既有裂缝**：模板把有数据的自定义列设为隐藏时，
  `recalc` 照样把值计入应收合计，屏上会出现"合计对不上明细"。
  这个坑**今天就存在**，与本次改造无关，单独决定是否修。
