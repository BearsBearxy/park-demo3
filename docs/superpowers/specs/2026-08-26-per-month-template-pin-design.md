# 账册模板：版本按「册 × 月份」独立选择

> 2026-08-26 拍板。**修订** `2026-08-25-global-book-template-design.md`：
> 那份的 R1/R7/R8/R9 保留，**R2 改写**，**R3 / R4 / R6 删除**，R5 换形态。
> 本次台账与附表10 **两屏同做**。

## 1. 为什么改

上一轮把模板收成全局一条链、每司一个指针。跑起来暴露两个问题：

**① 指针太粗，一改就是一整家公司。**
版本指针挂在公司上，改一次模板，该公司**所有年月**的台账一起换列。但账册天然是按月记的——
2024 年的源册长一个样、2026 年的长另一个样，硬要它们共用一套列，等于逼用户在
"历史月显示错列"和"新月份用不了新列"之间二选一。

**② 升级被做成了待办事项，还挡住编辑。**
只能升到最新版、不能选旧版；不升就顶着红点，且 R3 的链尾门让编辑模式点不开。
本意是"不强制"，实际体感是"一直在催、还不让干活"。

**③（顺带）`hidden` 与合计口径的裂缝。**
前端 `bookTemplate.ts` 过滤 `hidden` 列不渲染，后端 `ExtraFees.sum` 全口袋照加。
两边都是**故意**这么写的（`bookTemplate.ts:9` 注释明写"合计口径含隐藏列"），
但合起来的效果是：**钱算进合计了，列却不给看** —— 屏上合计永远对不上明细。

## 2. hidden：只能往显示侧修

**禁止**让 `recalc` 跳过隐藏列。归档一个列会让**所有历史月的应收凭空变小** →
`balanceEnd` 变 → 整条结余链被改坏。这比"合计对不上明细"严重一个数量级。

**修法**：自定义列在**该月有非零值**时一律显示，且**只读**（不接受录入）。
`hidden` 的语义收敛成「不再接受新录入」，而不是「藏起已经发生的钱」。

结果：合计恒等于明细之和；`LedgerService.recalc` 与 `ExtraFees.sum` **一行不动**。
两屏同修（`S10Service` 走同一个 `ExtraFees.sum`，前端 `bookTemplate.ts` 两屏共用）。

## 3. 核心规则

### P1 一条链（沿用 08-25 R1）
每屏的模板版本挂在一条链上，版本号只追加、不改写。台账一条；附表10 按期区各一条。

### P2 pin 键 = (册, 年, 月)
版本指针从「每册一个」改为**每册每月一个**。台账的册=公司，附表10 的册=期区。
这是该月**列定义与导入词典的唯一来源**。

### P3 解析顺序
读某月生效的版本时，**在同一个册的 pin 里**依次：

1. 该月的显式 pin
2. **最近一个更早月份**的 pin（沿用上月；跨空月继续往前找，不跨册）
3. 该册所在链的链尾

第 2 条与结余链的「严格相邻」**故意不同**：结余链跨空洞前滚会改坏钱，模板只决定显示与词典，
往前找最近一版既安全又符合直觉。第 3 条只在该册一个 pin 都没有时命中（如全新公司的第一个月）。

### P4 编辑 = 从本月那版长出新版，只带走本月
「编辑模板」打开的是**当前月正在用的那一版**，改完存成 `链尾版本号 + 1` 的新版本，
然后**只把当前月**切到新版。同册其他月份、其他册一律不动。

所见即所改。代价是"版本号大"不再等于"内容更全"——这是有意的：既然谁也不被强制往前走，
版本就该是**一套列的快照**，不是演进的一步。

### P5 版本选择器，无红点
编辑按钮旁一个 `v3 ▾`：显示本月生效版本，下拉列出全链（最新那版标「最新」），选中即切本月。
**不再有红点、不再有"升到 vN"按钮、不再因为落后而锁编辑门。**

### P6 权限（沿用 08-25 R9）
编辑模板与切版本同走第 16 权限点 `book-template:edit`。查看链与历史定义（GET）全员可读。

### P7 删列守卫：保留，但收窄到「当前月」
`assertNoDataLossOnCustomRemoval` 继续拦「把名下有数据的自定义列从模板里删掉」，
但检查范围从"所有公司"收窄为**正在编辑的那一个月**——按 P4，只有这个月会切到新版本，
别的月还钉在旧版上、列还在，与它无关。

保留它的理由不是显示（显示已由 §2 兜住），而是**行保存时 `extraFees` 是整包替换**
（`LedgerSaveRow.extraFees` 非空=整包替换）：草稿里没有的键会被抹掉。

## 4. 删除的规则

| 08-25 的规则 | 处置 | 为什么 |
|---|---|---|
| **R3** 只能在链尾编辑 | **删** | P4 下编辑永远产出链尾+1，「非链尾编辑」这个概念不存在了 |
| **R4** 编辑只带走链尾上的公司 | **删** | 换成 P4「只带走当前月」 |
| **R6** 切版本受归档守卫拦截 | **删** | 它防的是"列没了钱还在合计里"；§2 修好显示后，切到任何版本都藏不了钱 |
| R5 升级提示 / 红点 | **换形态** | 换成 P5 的选择器 |
| R1 / R7 / R8 / R9 | 保留 | 一条链 / 切指针不造版本 / 可跨版跳 / 权限 |

净效果是**少三条规则**，且少了两处会拦住用户的 409。

## 5. 数据模型

```
book_month_pin                                  ← 新表
  id            BIGINT PK
  screen        VARCHAR(12)   -- ledger | s10
  owner_id      INT           -- ledger=company_id;  s10=phase(1..4)
  period_year   SMALLINT
  period_month  TINYINT
  version_id    BIGINT        -- → book_template_version.id
  UNIQUE KEY uk_pin (screen, owner_id, period_year, period_month)
```

`owner_id` 从册行推出来，不由前端传：`screen='ledger'` 取 `ledger_book.company_id`，
`screen='s10'` 取 `ledger_book.phase`。接口路径上仍是 `/api/books/{bookId}/...`，
服务端负责 book → (screen, owner_id) 的映射，前端不需要知道这层。

⚠ **`s10_record.acct_month` 是 `CHAR(7)` 的 `'YYYY-MM'`**，不是 year/month 两列
（台账 `monthly_ledger` 才是 `period_year` / `period_month` 两个整数列）。
`book_month_pin` 统一用两个整数列，所以 s10 侧的迁移与查询都要**拆/拼** `acct_month`。
统一成整数列是有意的：pin 表要按「同册更早月份」倒序找最近一条（P3 第 2 步），
字符串月份排序虽然在 `'YYYY-MM'` 下恰好正确，但把这个巧合写进索引扫描不值得。

`ledger_book.current_version_id`：
- **宿主行**（台账全局链）继续标链尾，是 `latestVer` 的来源
- **附表10 的期区册**同样继续标自己那条链的链尾
- **台账的公司册**这一列就此作废，迁移时置 NULL，并在实体上注明只对链宿主有意义
  —— 留一个半死不活的字段，迟早有人拿它当"当前版"用

## 6. 接口

| 端点 | 变化 |
|---|---|
| `GET /api/books/{id}/template/at/{year}/{month}` | **新增**。按 P3 解析，返回 `{id, screen, owner, name, ver, latestVer, definition}`。前端取列一律走它 |
| `POST /api/books/{id}/template/pin` | **取代 `adopt`**。body `{year, month, ver}`，只钉这一个月，不造版本 |
| `PUT /api/books/{id}/template` | body 增 `{year, month}`：从该月那版改起，存成链尾+1，只把该月切过去 |
| `GET /api/books?screen=` | `definition` 语义改为**链尾版**（编辑器与导入中心的兜底用），另有 `latestVer` |
| `GET /api/books/{id}/template/versions` | 不变（返回全链）；`current` 改为"本月生效版"需带 `year/month`，不带则标链尾 |

`BookService.customIdsByCompany(companyId)` → `customIdsAt(screen, ownerId, year, month)`，
导入校验按 (册, 月) 取自定义列白名单。**导入词典跟着月份走，不是跟着公司走。**

## 7. 迁移（V111）

1. 建 `book_month_pin` 表
2. 每个**已有数据**的 (公司, 年, 月) → pin = 该公司册当前的 `current_version_id`
   （数据来源：`SELECT DISTINCT company_id, period_year, period_month FROM monthly_ledger`）
3. 每个已有数据的 (期区, 年, 月) → pin = 该期区册当前的 `current_version_id`
   （数据来源：`SELECT DISTINCT phase, acct_month FROM s10_record`；
   `acct_month` 是 `'YYYY-MM'` 字符串，拆成 `period_year` / `period_month` 两个整数）
4. 台账公司册的 `current_version_id` 置 NULL
5. 没数据的月份**不建行**，靠 P3 解析兜

迁移后用户看到的每一个月，列与迁移前**逐字节相同**。

归并逻辑同样放启动幂等方法（沿用 `migrateToGlobalLineage` 的位置与模式），
V111 只建表；幂等键 = `book_month_pin` 是否已有行。

## 8. 测试

**核心断言（本次的存在理由）**
- 改某月的模板 → **同册其他月份不变、其他册同月份不变**
- `recalc` 结果在改模板前后**逐分不变**（钉死"不许往 recalc 侧修"）

**解析（P3）**
- 本月有 pin → 用它
- 本月无 pin、上月有 → 用上月
- 本月无 pin、上月也无、更早有 → 用更早那个（跨空月）
- 该册一个 pin 都没有 → 链尾

**编辑（P4）**
- 从钉在 v2 的月份编辑 → 产出 `链尾+1`，内容基于 v2；只有该月切过去
- 编辑不再因为"不在链尾"被拒（08-25 R3 已删，回归断言）

**hidden（§2）**
- 归档列在**有非零值**的月份显示、且只读（不可录入）
- 归档列在**无值**的月份不显示
- 两屏都测（台账 + 附表10）

**守卫（P7）**
- 删掉在**当前月**有数据的自定义列 → 409
- 删掉只在**别的月**有数据的自定义列 → 放行（那些月还钉在旧版上）

**导入**
- 导入词典按 (册, 月) 取：月份钉在不含某自定义列的版本 → 该列是未知 id，记名跳过

**迁移**
- 迁移后每个已有月份的 definition 与迁移前逐字节相同
- 幂等：重跑不产生第二批 pin

## 9. 明确不做

- **批量应用**（应用到本年 / 所有月份）。有了 P3「沿用上月」，新月份自动继承，
  真正要手工切的只有已存在的月份 —— YAGNI，等真痛了再加
- **模板的时间生效区间**（"v3 从 2024-01 起生效到 2025-12"）。pin 已经能表达同样的事，
  多一套区间语义只会和 pin 打架
