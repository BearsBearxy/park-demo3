### 0.2 三层身份键为什么全落空

| 层 | 键 | 结果 |
|---|---|---|
| L1 编码 | `codeKey` | 原册无码 → 落空 |
| L2 位置 | `addrKey = kind\|zone\|area\|spot\|subName` = `elec\|p1\|B座\|天面\|电表①` | **3 个候选(281/282/283)** → 抛歧义 |
| L3 标识名 | `kind\|zone\|name` | 用户文件**丢了 A 列** → 行名回落成 `B座-天面-电表①` → 落空 |

用户文件丢 A 列的机制：`meterExcel.ts:102` 以「区域是否在第 0 列」判断有无标识列——
```ts
const nameCol = areaCol > 0 ? 0 : -1
```
原册「区域」在 B 列（A 列是无表头的标识列）；用户复制出来的那份**表头首格就是「区域」** → `areaCol = 0` → `nameCol = -1`。报错里显示的行名 `B座-天面-电表①` 正是 `fallbackName` 的拼接结果，即实锤。

### 0.3 缺陷本体

`MeterService.Idx.pick()` 在 L2 歧义时**只按标识名 `name` 再筛一次**，不按企业名称筛：
```java
if (name != null) { ... filter(m -> name.equals(m.getName())) ... }
return new Match(null, by, "按位置匹配到多块表…");
```
而 `addrKey` 也不含企业名称。**原册里区分这三行的恰恰就是企业名称**，库里 281/282/283 的 `tenant_name` 正是 `东侧楼梯间消防照明 / 西侧楼梯间消防照明 / 东侧货梯`，两两不同。

## J1 位置歧义时按企业名称再筛一次

`pick()` 在按 `name` 收窄之后、抛歧义之前，**再按企业名称收窄一次**：

```
候选去掉编码冲突者 → 唯一则命中
→ 按标识名 name 收窄 → 唯一则命中
→ **按企业名称 tenantName 收窄 → 唯一则命中**      ← 新增
→ 仍多 → 抛歧义
```

- 比较用 `trim()` 后精确相等；**不做模糊匹配**（模糊会把「许振虎」和「许振虎临电」并成一个）。
- `tenantName` 为空的导入行跳过这一层（不能用空值去筛）。
- **`addrKey` 不动** —— 改键会重排全库匹配行为，风险远大于收益；只在歧义分支加一道收窄。

## J2 报错文案改准

现文案「请补表编码或细化位置后重导」是**误导**：原册这四行本来就没有编码（补不了），「天面」已经是原册原文（细化它就偏离账册）。

改为分情况给**可执行**的出路：
- 若导入文件**缺标识列**（见 J3 判定）：`第 N 行「X」按位置匹配到多块表(id …)，且本文件缺原册首列(标识名)、企业名称也未能区分。请用「下载模板」或「导出当月」得到的文件重导（两者都带标识列）。`
- 若**有标识列但仍歧义**：`…标识名「Y」与企业名称「Z」都未能唯一命中，请核对档案。`

## J3 导入预检：缺标识列要说出来

`parseMeterSheet` 检出 `areaCol === 0`（表头首格即「区域」= 无标识列）时，在导入结果的 **notices**（刀F 已把 notices 与 errors 分开）里出一条：

`本文件缺原册首列(标识名)，同位置同表号的行将只能靠企业名称区分；建议用「下载模板」或「导出当月」的文件重导。`

**不阻断导入** —— 大多数行靠编码/位置就能命中。

## J4 模板与导出必须带标识列（治本）

只要用户手头的文件没有标识列，这个坑就会反复。检查并保证：
- `下载模板` 的表头**第一列是标识列**（与原册同构：无表头的窄列）；
- `导出当月` 的产物同样带标识列，且值 = `meter.name`。

若已满足则只需在提交物里给出证据；不满足则补上。
