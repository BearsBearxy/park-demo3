# 灵睿 LinkSight 更新公告规范

> 这份规范管三样东西：版本号、`frontend/src/changelog.ts` 里的每一个字、「本次更新」弹窗对用户的打扰。
> 它是 `docs/design/VERSION-UPDATE-SPEC.md` 的下位规范。§2 的分组语义、§3 的弹出规则、§8 的「同一个 PR 里做完」都继续有效。本文改动它们的地方会标 **〔改〕**。
> 标 **【需要改代码，未实现】** 的，是现在的代码做不到的。这类条目后面会写「在那之前怎么做」。
> 数字后面标「依据」的来自对标调研，标「自定」的是我们自己选的，理由写在同一句里。

---

## 0. 一句话总则

**合并就是发版**，所以每个用户看得见的 PR 就是一版公告：一个版本号、一段 `changelog.ts`，整版不超过 450 字（见 §7）。**功能更新自动弹「本次更新」，小调整不弹、只亮 ✦ 蓝点**；是哪一种按 §2.1 的判定表定，版本号跟着定（§1），弹不弹由版本号自动决定。

---

## 1. 版本号规则

版本号只有一个来源：`frontend/package.json` 的 `version`，格式 `MAJOR.MINOR.PATCH`，不加 `v` 前缀（依据 SemVer FAQ）。

| 这个 PR 里用户看得见的改动（§2.1 判定） | 怎么涨 | 弹不弹 | 例 |
|---|---|---|---|
| **功能更新**：有新增、用法变了、金额或数量会变、删了屏或入口 | MINOR +1，PATCH 归 0 | 自动弹 | 0.14.0 → 0.15.0 |
| **小调整**：修复（不改金额）、文字 / 样式 / 布局微调、提示更清楚、变快 —— 用户不太能明显感觉到的 | PATCH +1 **〔改〕** | 不弹，只亮 ✦ 蓝点 | 0.15.0 → 0.15.1 |
| 用户看不见（测试、构建、日志、内部整理） | 不涨，不写公告 | — | — |
| 用户要重新学用法（导航整体换掉、老数据要迁移或重录） | MAJOR +1，其余归 0，**由用户拍板** | 自动弹 | 1.4.2 → 2.0.0 |

- **〔改〕VERSION-UPDATE-SPEC §8 第 1 条**：原来写的是「每版次版本号 +1」。现在改成「小调整涨 PATCH」（那边已同步）。**用户 2026-09-19 拍板**：只要是功能更新都要弹；普通小调整、用户不太能明显感觉到的，不弹。依据：VS Code 的只修复版涨第三位（1.100.1），M365 只修复时只涨 build，SemVer 定义 PATCH 就是修复。
- **功能更新不许记成小调整**。只有改进、没有新增的功能更新版不写重点卡，也不换配图（§3、§5），所以不存在为了省事而降成 PATCH 的理由。
- **不再用预发布后缀**（`-beta.1` 这类）。我们只有一台服务器、没有预览通道，带后缀的版本和正式版一样推给所有人，后缀没有意义（自定）。历史上的 `0.10.0-beta.1` 保留不动。还在试用的功能，在标题末尾写「（试用）」。这个做法对标 Figma 的 Beta 标签和钉钉逐条标 beta。
- **0.x 期间 MINOR 就是常规发版单位**（依据 SemVer：0.y.z 属于初期开发，每版涨 MINOR）。
- **什么时候到 1.0.0**：同时满足下面两条，就在下一个 MINOR 发版前请用户拍板（自定，比照 SemVer「用于生产、用户依赖它」的判据）：
  1. 连续 2 个自然月，月结（抄表 → 核算 → 催缴单 → 台账 → 三大报表）都在系统里完成，没有回到 Excel 补账。**这一条系统里没有记录，由用户确认，不由 agent 判**；
  2. 那两个月里，没有一版改变已结账月份的金额。
- **1.0 以后的 MAJOR**：只因为「用户要重新学」才涨，不因为技术换代涨（依据：飞书 V7→V8 用了几年，Chrome 文档说 MAJOR 是排期和市场上的决定）。

### 1.1 两个 PR 抢同一个号

合并即部署。两个 PR 都会改 `package.json` 里 `version` 那同一行，所以后合并的那个一定在这一行上冲突，GitHub 会拦住它。这个冲突就是护栏，不要用「合并时自动解决」绕过去。

后合并的一方按这个顺序做：

1. `git fetch && git rebase origin/master`，冲突时保留 master 的版本号；
2. 在 master 的版本号上按 §1 的表重新涨，比如 master 已经是 0.15.0，你有新增，就改成 0.16.0；
3. `changelog.ts` 里把自己那段挪回最前面，`version` 改成新号，`date` 改成当天；
4. 只跑 `changelog.spec.ts`，绿了再推。

同一天可以有多个版本，日期相同不算违规（现在的 spec 只要求日期不递增）。

## 2. 什么时候写公告，什么不写

判据沿用 VERSION-UPDATE-SPEC §8：**这个改动用户在屏上看得见吗**。看得见的，再按 §2.1 分成功能更新和小调整。

| 写 | 不写 |
|---|---|
| 新屏、新按钮、新的导出或打印 | 测试、构建、CI、依赖升级 |
| 用法变了：点同一个地方结果不同、落点变了、默认值变了 | 代码整理、改名但屏上字没变 |
| **金额、数量会变**：算法、分摊规则、取数范围改了 | 只有日志或控制台里能看到的报错 |
| 修了用户碰得到的错：算错、点不动、没提示 | 用户碰不到的边界情况（写进 PR 描述） |
| 删了一屏或一个入口 | 还没修好的问题（我们没有「已知问题」一组，见 §3） |

- **金额会变的改动必须写**，而且要写清三件事：**从哪个月起、哪些数会变、已结账的月份变不变**（自定：财务产品最怕的是「数悄悄变了」。依据相近：Microsoft .NET 的破坏性变更模板要求写「原来 / 现在 / 要不要做什么」）。
- **删屏或删入口**：写进「改进」，句式「原来在 X，现在到 Y」。如果用户没有替代去处，删之前那一版就要在公告里预告「下一版起 …」（依据：GitLab 要求提前告知移除，GitHub 在生效当天发 Retired）。


### 2.1 功能更新还是小调整（决定版本号和弹不弹）

从上往下问，**碰到第一个「是」就是功能更新**；四个都「否」才是小调整。

| # | 问题 | 例 |
|---|---|---|
| 1 | 有新增吗？新屏、新按钮、新的导出或打印、新入口 | 首页、收藏、对账单导出 |
| 2 | 用法变了吗？点同一个地方结果不同；登录后落点、左侧导航、顶栏、页签条变了；默认值变了 | 点导航从换预览页签改成换当前页签 |
| 3 | 屏上已有的金额或数量会变吗？算法、分摊规则、取数范围改了 —— **修复也算**，只要修完数会变 | 公共电分摊少算的修好了，催缴单金额会变 |
| 4 | 删了一屏或一个入口吗 | 某个按钮挪走了 |

小调整就是剩下的：不改数的修复、文字 / 样式 / 间距、提示写得更清楚、加载变快。**拿不准就算功能更新**（多弹一次的代价比该知道的没看到小）。

一个 PR 里两种都有，按功能更新算，小调整的条目一起写进这一版。

## 3. 内容结构

弹窗里的顺序由代码定死，不能改：**页头（版本号 + 一句话标题）→ 重点卡 → 新增 → 改进 → 修复 → 底栏**。空的组自动隐藏（已实现）。

| 块 | 字段 | 必填 | 条数上限 |
|---|---|---|---|
| 一句话标题 | `headline` | 必填 | 1 |
| 重点卡 | `feature` | 这一版有新增：必填，放最重要的那条新增；没有新增（只有改进的功能更新版、小调整版）：不许写 | 1 |
| 新增 | `added[]` | 选填；没有 `feature` 时必须为空；小调整版不许有 | 新增 + 改进合计 ≤ 6（不算重点卡） |
| 改进 | `improved[]` | 选填；小调整版里写那些小调整 | 同上 |
| 修复 | `fixed[]` | 选填；小调整版的改进 + 修复至少 1 条 | ≤ 5 |

- **上限 6 和 5 是自定的**。依据：GitLab 的 What's new 每版 3–7 条。另有一个类比：Chameleon 测的产品引导，3–4 步的完成率 72–74%，7 步以上只有 16%（测的是引导步数，不是列表条数）。超出时先把同一屏的多条合成一条，还超就说明这一版太大，应该拆成两个 PR。
- **重点卡只放「新增」性质的东西**。原因：重点卡的标签在代码里写死为「新增」（`WhatsNewDialog.vue` 重点卡那段），更新记录里它也算进「新增 N 项」（`ChangelogDialog.vue` 的 `addedCount`）。所以：
  - 有新增 → 最重要的那条新增提成 `feature`，其余新增进 `added`；
  - 没有新增 → 不写 `feature`，最重要的改进放「改进」第一条，并写进 `headline`。
  - 重点卡改用「改进」标签属于 **【需要改代码，未实现】**。
- **排序**：每组内按「用法变了 → 金额会变 → 其余按侧栏里的先后」排（自定，依据相近：Apple 要求 What's New 按重要性排）。
- **不做的结构**：
  - 按模块分组（钉钉、企业微信、金蝶的做法）**【需要改代码，未实现】**。我们每版 ≤ 7 条，分组意义不大，在那之前靠标题写屏名来定位。
  - 「已知问题」一组 **【需要改代码，未实现】**。在那之前不写没修好的问题。
  - 「管理员 / 普通成员」分开发（飞书、企业微信的做法）**【需要改代码，未实现】**。在那之前，只和系统管理员有关的条目，在说明开头写「系统管理员：」。

## 4. 每一种文字的写法与字数

字数按字符数算，中文、英文字母、数字、标点各算 1 个，**空格不算**（§4 通用规则 9 要求中英文之间加空格，不能让它吃掉字数）。**句数按句号「。」数**，分号「；」连起来的算同一句。

| 文字 | 字数 | 句数 | 允许的句式 | 不许 |
|---|---|---|---|---|
| `headline` | 8–20 | 1 句，最多 1 个逗号 | 「<做成了什么>，<第二件事>」 | 句号、感叹号、「全新 / 重磅 / 大幅」 |
| 重点卡 `title` | 2–12 | — | 侧栏屏名；不是一屏时写「<谁>能<做什么>」的短语 | 功能内部名、英文缩写 |
| 重点卡 `desc` | 40–100 | ≤ 4 句 | 「点 X，Y」「在 X 里能 Y」，说清入口和结果 | 讲实现原理、写会过期的数 |
| 条目 `title` | 2–12 | — | 同重点卡 | 同上 |
| 条目 `desc` | 10–45 | 1–2 句 | 新增：「能 …」；改进：「原来 …，现在 …」或「… 了」 | 「优化了体验」这类空话 |
| 修复一行 | 15–45 | 1 句 | 「<屏名>：<原来的现象>」或「<屏名> <动作>，原来 <现象>」 | 「修复了若干问题」「解决已知问题」、写原因不写现象 |
| `toLabel` | 2–6 | — | 「去看看」（默认）或「去<屏名>」 | — |

字数的来历：`headline` 参考飞书版本标题中位数 21 字；条目按 GitLab 标题 ≤ 7 词、飞书小标题约 10 字，再对照 0.14.0 的实际长度；一段按阮一峰指南「20 字以内最好、超过 40 字不行」，我们取硬线 30（自定）。**「一段」的切法**：遇到 `，。；：！？（）` 就切开，顿号 `、` 不切。

**通用规则**（前三条已有，后面是新增）：

1. 用用户的话；标题等于侧栏里那一屏的名字；不写开发用语（`changelog.spec` 的禁词表）。
2. 不提设计稿；写测量出来的事实，不写定性（屏上文案三条）。
3. 修复写「原来哪里不对」，而且先对照 master 核实原来确实如此（VERSION-UPDATE-SPEC §8 第 2 条）。
4. **写现象，不写原因**：「催缴单金额少算了公共电」可以，「修正分摊查询条件」不行（依据：GitHub Docs 的修复模板要求描述原来的行为，Featurebase 用现象对比原因的例子）。
5. **用法变了**，统一写成「原来 …，现在 …」。如果变的地方是**登录后落点、左侧导航、顶栏、页签条**之一，还必须写进 `headline`（自定：这四处每个用户每次登录都会经过）。
6. **金额会变**，说明里必须有：起始月份、会变的数、「已结账的月份不变 / 会变」。
7. **不写会过期的数**：行数、屏数这类随后续版本变化的数不写（0.13.0 的教训：「记账 8 行」写上去就对不上了）。写了数，就要能在源码里找到出处。
8. 不用感叹号、不用 emoji。只有屏上真实出现的符号可以写，比如收藏按钮的 ☆（依据 Mailchimp：感叹号要少用；另有我们产品界面不用 emoji 的规矩）。
9. 中文和英文、中文和数字之间空一格（「按住 Ctrl 点」「最多 12 个」）。标点用全角，不叠用（依据：中文文案排版指北）。
10. 每一条都要能单独看懂，不写「上一版提到的 …」。跳过版本的人只看得到最新一版（§3）。

## 5. 配图（重点卡右侧那块）

**现状**（2026-09-19 起）：重点卡是共用组件 `components/shell/release/ReleaseFeatureCard.vue`，「本次更新」弹窗和「更新记录」都用它。配图**每版一个组件** `components/shell/release/Art<版本>.vue`（如 `Art0140.vue`），登记在同目录 `art.ts` 的 `RELEASE_ART`，卡片按版本号取图 —— 不再覆盖上一版的，关掉弹窗后在更新记录里翻到那一版还看得到。配图宽 200px、内宽 178px，高度随卡片拉伸；用 HTML/CSS 手搭的静态示意，带 `aria-hidden`；不支持图片文件。

| 规则 | 内容 |
|---|---|
| 什么时候画 | 有 `feature` 就新建一个 `Art<版本>.vue` 并登记进 `art.ts`（VERSION-UPDATE-SPEC §8 第 3 条），不改、不删旧版本的图。没有 `feature` 的版本（只有改进的功能更新版、小调整版）不画 |
| 画什么 | 这一版重点的**缩样**：新屏或新控件最关键的那一眼，≤ 4 行或 4 个元素。颜色从对应的真实组件抄（照 0.14.0 的 `Art0140.vue` 从 TabStrip 抄色） |
| 字 | 只用字阶里的 12 / 11px；屏名、按钮名和产品里一字不差；数据要像真数据，不写「测试 / 示例」（依据：GitLab 要求真实数据） |
| 尺寸 | 不能撑高卡片；「本次更新」（560 宽）和「更新记录」（右栏约 540 宽）都要看；S 档（< 600px）重点卡改为上下排，也要看一眼 |
| 不画 | 动画（配图一律静止）、产品里没有的元素、营销插画 |
| 读屏 | 配图带 `aria-hidden`，所以**重点卡的文字不看图也要能讲清**（依据 WCAG 1.1.1 对装饰性内容的要求：装饰图对读屏隐藏，信息必须在文字里。这一条不来自对标调研） |
| 截图 | **【需要改代码，未实现】**，也不打算做：手搭缩样跟随配色、清晰、不增加资源体积。万一要做，规矩是 PNG/WebP、2 倍图（356px 宽）、≤ 150KB（依据 GitLab）、有 alt、放在仓库里自己托管 |
| 其他条目 | 不配图（依据：Linear 的 Fixes / Improvements 列表不配图；企业微信只修复的版本 0 张图） |

## 6. 动图 / 视频

**不用。** 理由：

- 配图位只有 178px 宽，演示不了一段操作；
- 弹窗在登录后自动出现，自动播放等于在用户开工前再打扰一次（依据 NN/g：登录后立刻弹窗是弹窗十大问题的第 2 条；我们自己的弹窗为什么仍然登录后弹，见 §7「何时弹」）；
- 超过 5 秒的动效必须能暂停（依据 WCAG 2.2.2、G152）；静音自动播放的视频浏览器不会因为「减少动态效果」而自动停，要自己写代码判断（依据 WHATWG #11605）；
- 同类中国 B2B 产品的公告也基本只用静态图：飞书 V7.65 8 张 PNG、企业微信 5.0 39 张 PNG，都没有视频；钉钉 8.5.5 黑板报 60 张 PNG、0 个视频。

如果以后必须要，属于 **【需要改代码，未实现】**，规矩先定好：

- 不用 GIF，用 MP4 或 WebM（依据 web.dev：同一段动画体积小 85–91%；GitLab 旧规也是 GIF 超过 300KB 就改用视频）；
- 时长 ≤ 5 秒的可以循环自动播放，超过 5 秒必须带控件、点了才播；
- 有封面图；开启「减少动态效果」时只显示封面；
- 单个文件 ≤ 300KB，放在仓库里自己托管（自定：VS Code 1.104 的 7 段演示视频里，5 段在 226–335KB 之间，取这个区间的中段）。

## 7. 用户观看体验

| 项 | 规则 | 状态 |
|---|---|---|
| 何时弹 | **只在功能更新时弹**：到当前版本为止最新的那版功能更新（版本号最后一位是 0），这个账号还没看过；本次页面加载还没弹过；不在编辑态；壳挂载后延迟 `POPUP_DELAY_MS = 1200`。这和 NN/g、Material「不在登录 / 打开应用时弹」相悖。保留的理由：用法变了（比如登录落点）如果不在登录时说，用户会先在旧地方找不到东西，而我们没有别的渠道告诉他。缓解：编辑态不弹、每版一次、小调整不弹 | 已实现（2026-09-19） |
| 频率 | 每账号每浏览器每版功能更新弹一次（已读记在 localStorage 的 `fp-seen-version:<账号>`，换电脑或清了浏览器数据会再弹一次）；每次页面加载最多弹一次 | 已实现 |
| 两次自动弹的间隔 | **不设**。用户 2026-09-19 拍板：功能更新都要弹（原来提的「隔 3 天」依据 Intercom，被这条取代）。同一天有几个功能更新，尽量在合并前攒进同一个 PR，一次发一版 | 规矩 |
| 跳过的版本 | 弹最新那版功能更新（当前是 0.15.1、这个账号只看过 0.14.0 → 弹 0.15.0 的内容）；其余在「更新记录」里 | 已实现（2026-09-19） |
| 小调整版 | **不自动弹**，只亮顶栏 ✦ 蓝点、更新记录里标「新」（依据：VS Code 只在涨 major/minor 时自动打开发布说明） | 已实现（2026-09-19） |
| 什么算看过 | 关掉「本次更新」（四种关法都算），或打开「更新记录」。记下的是**当前版本**：弹的是 0.15.0、当前是 0.15.1 时，关掉弹窗 0.15.1 也算看过，它的小调整在更新记录里能翻到 | 已实现（2026-09-19） |

## 8. 流程与检查清单（每个用户看得见的 PR）

1. **判定**：用户看得见吗？看不见 → 不涨版本号、不写公告，结束。
2. **定号**：按 §2.1 判定表定功能更新还是小调整；`git fetch`，读 master 的版本号，功能更新涨 MINOR、小调整涨 PATCH，改 `package.json`。弹不弹由版本号自动决定，不用另外设。
3. **写条目**：在 `changelog.ts` 最前面加一段，`date` 写当天（北京时间）。按 §3 定结构（有新增才写 `feature`），按 §4 逐句数字数、数每一段。
4. **修复要核实**：每一条修复都在 master 上确认原来确实如此（VERSION-UPDATE-SPEC §8 第 2 条）。
5. **配图**（只有带 `feature` 的版本）：在 `components/shell/release/` 新建 `Art<版本>.vue`、登记进 `art.ts`，然后桌面宽和 375 宽各渲染看一眼，「本次更新」和「更新记录」两处都看。
6. **自测**：只跑 `changelog.spec.ts` 和 `versionUpdate.spec.ts`，全量测试留到收口时再跑。
7. **核文案**：派 `screen-copy-adversary` 逐句对照源码，查出的问题改掉。
8. **先推再交**：以上所有提交在 PR 交给用户**之前**推上去。PR 描述写一句：「版本号 X，公告讲了 N 条：……」。
9. **合并前**：如果 master 动过，按 §1.1 重新定号。
10. **合并后**：打开线上，底部出现刷新提示 → 刷新 → 确认弹出的是这个版本号。

## 9. 自动检查（`changelog.spec.ts`）

**已有**（不动）：

1. 第一段的版本号等于 `package.json`；
2. 日期从新到旧；
3. 版本号不重复；
4. 日期格式 `YYYY-MM-DD`；
5. 「去看看」指向真实存在的屏；
6. 图标名在 `icon.ts` 的表里；
7. 文字不为空；禁词：`重构 门禁 口径 refactor commit 提交记录 设计稿 chunk store`。

**已加**（2026-09-19，`changelog.spec.ts` 里「更新公告规范」那一组）。只检查 0.14.0 及以后的版本 —— 更早的版本写在这份规范之前，不回头改：

8. 版本号符合 `^\d+\.\d+\.\d+$`，不带预发布后缀；
9. 版本号按语义从大到小，比较规则逐位比数字；
10. PATCH ≠ 0 的版本（小调整）：`feature`、`added` 都为空，`improved` + `fixed` 至少 1 条；
11. PATCH = 0 的版本：没有 `feature` 时 `added` 必须为空（有新增就必须把最重要的一条提成重点卡；没有新增就不许有重点卡）。重点卡是不是真的「新增」性质，归人工看；
12. 各段字数在 §4 表内（headline 8–20，title 2–12，feature.desc 40–100，desc 10–45，修复 15–45，toLabel 2–6）；
13. 条数：新增 + 改进 ≤ 6，修复 ≤ 5；
14. 整版总字数 ≤ 450；
15. 按 `，。；：！？（）` 切开后每一段 ≤ 30 字，顿号 `、` 不切；
16. 禁词表扩充 **〔改〕**：加上 `优化 若干 已知问题 bug Bug BUG 全新 重磅 大幅`；
17. 全部文字不许出现 `！` `!` 和 emoji（Unicode 表情区）；
18. `headline` 不许出现 `。`，最多 1 个 `，`；
19. 中文和英文、数字之间要有空格：正则 `[\u4e00-\u9fa5][A-Za-z0-9]|[A-Za-z0-9][\u4e00-\u9fa5]` 不许命中；
20. 修复条目不许以「修复」「解决」开头；
21. 同一版内标题不重复。
22. PATCH = 0 的版本（功能更新）至少有一条内容；
23. 0.13.0 起有 `feature` 的版本都在 `art.ts` 登记了配图；
24. `art.ts` 登记的每个版本都在 `changelog.ts` 里、而且有 `feature`。

第 10 条在出现第一个小调整版（0.x.y，y ≠ 0）之前查不到数据，是空转的；弹不弹的逻辑本身由 `updateMinor.spec.ts` 用假数据钉住。

**只能靠人看**：标题是不是侧栏屏名、改进是不是写了「原来 …，现在 …」、说明里的数在源码里有没有出处、配图画的和产品是否一致、重点卡是不是「新增」性质。这些归 `screen-copy-adversary` 和第 8 节第 5 步。

## 10. 示例：0.14.0 按本规范改过之后

0.14.0 起草时还没有这份规范，对照后有两处不合规，发版前已经改掉：

1. **重点卡语义**：原来的重点卡是「页签和浏览器一样用」。可页签在 0.13.0 就有了，这一版是改进，却挂着写死的「新增」标签。现在改成：「首页」（新屏，带「去看看」）当重点卡；「页签和浏览器一样用」挪到「改进」第一条；拖动、右键菜单、+ 新建这些以前没有的能力，单独作为一条「新增」。
2. **修复分段**：原句第一个逗号前有 32 字，超过每段 30 字。现在改成「<屏名>：<原来的现象>」句式，三段分别是 24、8、8 字。

配图也跟着改成了首页缩样（页签条上首页那格是当前页签，下面是搜索框、收藏、最近打开）。在桌面宽度下渲染确认过：四块宽度都在 178px 以内，配图高 138px，没有撑高卡片。
