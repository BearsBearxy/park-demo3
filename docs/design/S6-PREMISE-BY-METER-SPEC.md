## §0 问题与根因（dev 库 2024-02 实测，双人交叉复核）

`BillNoticeService.premiseOf(contractId, locs)`（`:749`）把**该合同全部 distinct 计费行 location** 用「、」拼接后 `trunc(64)`，贴到每一条表行上。这是唯一违规点，三个调用点：

| 行号 | 用途 | 本刀是否改 |
|---|---|---|
| `:528` `meterLine()` | **全部电/水/管理费表行** | ✅ 改 |
| `:225` 容量费 | kVA 挂在合同上，合同级长串语义正确 | ❌ 不改 |
| `:697` `splitShare()` 非宿舍分支 | 公摊按合同拆、未按计费行拆 | ❌ 另刀（§4） |

**症状分布**（`ym='2024-02'`，全月 290 单 / 3359 行）：

| 口径 | 宿舍表行 | 非宿舍表行 |
|---|---:|---:|
| premise 含「、」 | 409 | 345 |
| premise 长度 > 20 | 355 | 230 |
| premise 恰好 64 字（**被 varchar(64) 永久截断**） | — | 全表 276 行 |

**两个根因，不是一个**：

- **B 类（拼接）**：合同有多条 location，`premiseOf` 拼起来。宿舍 266 行 / 非宿舍 241 行。
- **A 类（源数据合并录入）**：合同只有 1 条 location，但**原文自己就是多房号串**。改拼接逻辑一行都救不了。
  - 宿舍：仅合同 439（广联 S10-0081A#1），单条 location 124 字列 30 间房，**89 行**。
  - 非宿舍：18 份合同 / **104 行**（如 `二期10号楼（三车间）602、603、604单元`）。

→ **规则必须同时接住 A、B 两类**，否则 89+104=193 行原地不动。

**锚点可用性（复核确认）**：宿舍表 `meter.name` 就是裸房号（`309`/`309.00`），`room_no` 列 527 块全空（根因：`MeterService:675 ROOM_RE` 强制要求「室」字，宿舍册写法是「六楼 1-309」）；非宿舍房号 71.6% 在 `room_no`、其余大量藏在 `spot`。合并 `room_no⊕spot⊕name⊕sub_name` 后 **316/345 = 91.6%** 可提到房号。

**前端硬约束**：`billNoticeLogic.ts:127-131 byPremise` 靠 **premise 字符串全等 + 命中行唯一**把路灯/绿化水挂到房间行。今天表行是长串、公摊行是计费行 location → **几乎无一配得上**（实测全月仅 12 条配上、176 条落 extras），逐间面积列基本恒空。本刀让两侧同源，实测配对 **12 → 142**、extras **176 → 46**。

## §1 定案

| # | 条款 | 判据 |
|---|---|---|
| 1 | **表行 premise 跟表走，不跟合同走** | S5 §0#5 原文；本刀只兑现，不新增口径 |
| 2 | **取合同侧口径的文本，不用表侧自描述** | 公摊行 premise 来自计费行 location（`dormRoomsByContract` key）。表行必须产出**同一串**才能配对。自描述「一期 宿舍一栋309室」与纸约「保障房303室」不同源，会永久配不上 |
| 3 | **一刀连非宿舍一起修，不加 `if (dorm)` 分支** | 同一根因、同一机制；只修宿舍要多写一个分支且留 345 行同病行 |
| 4 | **合并串按房号合成单间文本** | 接住 A 类；`宿舍一栋309、310、…528室` + 表房号 309 → `宿舍一栋309室` |
| 5 | **匹配不唯一时回退今天的行为**，不猜 | 楼层/楼栋兜底会把厂房表判到绿化带空地（实测假阳性 cid 382），不做 |
| 6 | **金额一分不许动** | 本刀只改标签列；验收锚点见 §6 |

## §2 算法

### 2.1 房号 token 抽取

```
tok(s)        = { 最长连续数字段 r ⊆ s : 3 ≤ len(r) ≤ 4 }
roomTokens(m) = tok(m.room_no) ∪ tok(m.name)          若非空
              = tok(m.spot)    ∪ tok(m.sub_name)      否则
```

- **最长连续数字段**：`202007151529`（code）整段 12 位 → 直接落选，不会切出假 token；`309.00` → `{309}`；`1-309` → `{309}`；`2101、2102` → `{2101,2102}`；`501-504` → `{501,504}`。
- **`name`/`room_no` 优先于 `spot`**：复核已证 `name` 权威——表 929 `name=411.00` / `spot=五楼 1-516`，认 name 才对（516 另有其表，认 spot 会让 411 房没水表）。全月两侧不一致仅 3 只表，三条都是 name 正确；另有 14 只表 `spot` 楼层与房号矛盾（`spot=三楼401室` 实为第四层），认 `room_no`/`name` 反而修正了脏数据。
- **不读 `code`**（12 位流水号）与 `area`（楼栋标签如 `D座`）。
- ⚠ **`501-504` 只取端点 {501,504} 是刻意的召回牺牲**，不猜 502/503——区间中间号的表会零命中回退，不是 bug。当前 dev 库无此形态。

### 2.2 定位

```
resolveMeterPremise(meter, contractId, locsByContract):
    if contractId == null: return null
    locs = locsByContract[contractId]                 # 该合同 distinct 计费行 location，原序
    rt   = roomTokens(meter)
    if rt 为空 or locs 为空: return premiseOf(contractId, locs)      # 回退

    hits = [ L ∈ locs : tok(L) ∩ rt ≠ ∅ ]
    if |hits| ≠ 1: return premiseOf(contractId, locs)               # 回退（并 warn，见 2.4）

    L = hits[0];  inter = tok(L) ∩ rt
    if |tok(L)| > 1 and |inter| == 1:  return synthesize(L, inter 的唯一元素)
    return L                                                        # 原文，与公摊行同源
```

`|inter| > 1` 时**不合成**——表确实同时管几间（`一楼商铺 2101、2102`），原文才是对的。

### 2.3 合成 `synthesize(L, t)`

把 L 中「从第一个 token 起、到最后一个 token 止」的整段替换成 `t`，前后缀原样保留：

| L 原文 | 表房号 | 结果 |
|---|---|---|
| `宿舍一栋309、310、…、528室` | 309 | `宿舍一栋309室` |
| `A座孵化器四楼429室、430室、431室` | 430 | `A座孵化器四楼430室` |
| `二期10号楼（三车间）602、603、604单元` | 603 | `二期10号楼（三车间）603单元` |
| `一期C座二楼217、218、219室` | 218 | `一期C座二楼218室` |
| `二期9栋(车间二)101单元、102单元、5楼整层501-504单元` | 101 | `二期9栋(车间二)101单元` |

前缀=首 token 之前的原文，后缀=末 token 之后的原文。绕开「室 / 单元 / 号室」三套后缀写法，不做后缀字典。实测 48 条 distinct 合成逐条判读全部正确，含最刁的 `二期9栋(车间二)101单元、102单元、5楼整层501-504单元` + 101 → `二期9栋(车间二)101单元`。

⚠ **A 类单-location 合同（如 439 列 30 间房）对「表挂错合同」无护栏**：只要房号落在这 30 间里就会被自信地合成成单间且不告警。B 类多-location 合同则会 multi_hit 回退。这是 §2.3 拿精度换召回的固有代价，当前无实例。

### 2.4 回退告警（收窄口径）

**仅当 `roomTokens(m)` 非空且命中数 == 0**（真·零命中，即 D3 借表/挂错合同）才按户记一条短警告：`场地未定:{meter.name}`，`Set` 去重。

两类**不告警**（实测否则 63 条里有 16 条误报）：

- `no_token`——表压根没房号（开利暖通整栋表 7 只、翔海借电 D/E/F、三车间工地…）：无场地可定，告警永远消不掉，纯噪音。
- `multi_hit`——表合法地同时管几间（桑尼号电「二楼201、301室」、炳记电「四楼432-434室」）：与 §2.2 里「`|inter|>1` 取原文 = 已定场地」完全同构，判「未定」自相矛盾。

⚠ `bill_notice.warn` 是 `;` 拼接后 `trunc(255)`，`t14` 断言「缺起止日期」必须还在串里 → **警告必须短、按表去重、禁止逐行罗列**。实测最长一户 175/255，无一户超限。

### 2.5 `premiseText` 条目上限（防新引入的半截房号）

`:373` `premiseText = String.join(",", premiseOrder.keySet())` 再 `trunc(255)`。premise 变细后条目暴涨（合同 52 有 14 条、439 有 30 间），255 硬截会切出「宿舍一栋3」这种半截房号，前端 `aggregateByTenant` 按「,」拆项会把它当成一个场地。

→ 超过 **5** 项时取前 5 项 + `,等N处`，**N = 总项数**（「张三李四等5人」惯例，非剩余数）。这是本刀**新引入风险的对冲**，不是额外功能。

实测 11 张单触发收敛，收敛后 0 张仍 >255。⚠ 结构上未封顶（5 项 × 64 字理论可达 329 字仍会被 `trunc(255)` 拦腰切），当前数据不触发；日后 location 变长需复查。

**`premiseOf` 的回退串不做同款收敛**（cid 359 那 31 行仍是 64 字硬截、尾部「室」被吃掉）。理由：回退行本就是 §5 数据债的信号，收敛会让它看起来已解决；且收敛可能让同户不同合同的串塌成同一个键。

### 2.6 损耗分桶必须留在合同级粗粒度（金额护栏）

户级收尾的损耗循环按场地分桶落行，桶里同时收**非宿舍电表行**（本刀细化了）与**公摊行**（走 `splitShare→premiseOf`，§4 明令不改）。两侧改前同为合同级长串 → 同桶；若跟着细化，桶会裂开：

> 实测损耗行 124 → 143+，每条 `amount`/`base_snap`/`qty`/`note` 重写，月合计 3,535,971.77 → **3,535,971.75**，18 户受影响（旭化成一条 758.68 裂成 482.55 + 276.13）。

→ `L` 增字段 `premiseWide`（表行 = `premiseOf(contractId, locs)`，其余行沿用 `premise`），**损耗循环的所有分桶键/回填键一律用它**；排序、`premiseText`、落库仍用细粒度 `premise`。

这是 §2.2「改表行」与 §4「不改公摊行」两条决定的交点，S6-2 把公摊行也按计费行拆之后，损耗循环可整体切回细粒度。

⚠ **IT 对损耗链零覆盖**（`BillNoticeApiIT` 里 `share_elec_loss` 出现 0 次），所以 `mvnw verify` 全绿**不构成**这条的证据，只有 §6.1 的实测重生成算数。

## §3 前端配对键修正（同刀，否则界面先塌）

`billNoticeLogic.ts:127-131`：

```
现状：hit = rooms.filter(r => r.main.premise === premise);  return hit.length === 1 ? hit[0] : null
改为：先按 premise 过滤，再取这些行的 distinct meterId；
      恰好 1 个 meterId → 挂该表首行；否则 null（落 extras）
```

理由：**分时宿舍一间 = 一块表 4 段 = 4 行同 premise**，按行数唯一永远配不上（memory 记有 7 户分时宿舍）。按**表**唯一既修分时房，又保留「两间房同 premise 时不硬挂错间」的安全性（不同房=不同 meterId）——`spec:136-143` 那条用例语义不变。

`spec.ts` 需同步：`:92/:109` 两条把入参改成「表行=计费行 location 原文、公摊行=同一原文」的真实形态；`:121` 那条「现状兜底长串」从主路径降级为回退路径用例；新增一条「分时一表多段 → 路灯挂该表首行且只挂一次」。

## §4 不做（本刀边界）

| 不做项 | 理由 | 去向 |
|---|---|---|
| `splitShare` 按计费行拆场地 | 会改**行结构与逐行金额**（现按合同拆），撞可莱恩已验收锚点，须独立对账 | S6-2 另刀 |
| 容量费 premise | kVA 是合同级，长串语义正确 | 不改 |
| 楼层/楼栋兜底（Stage B/C） | 实测 +68 行但有假阳性（厂房表被判到「A座首层东侧绿化带空地」），且需「空地/天面/消防通道/人才港/车位」黑名单 | 待 §5 数据债清完再评估 |
| `meter.room_no` 回填 / `ROOM_RE` 口径 | 本刀在派生时抽 token，不依赖该列；且裸 SQL 回填会被下次导入 `applyDesc:604` 静默冲掉（须同改 `loc_manual|=4`） | 抄表模块另议 |
| 租金行 premise | 已是逐计费行 location（`:593`），不经 `premiseOf`；其长串 90 行属 §5 数据债 | 数据侧 |

**⚠ 已知副作用（本刀接受，不算 bug）**：非宿舍单的表行细化了、公摊/容量/管网行仍是合同级长串，`groupExcelStyle` 按 premise 分块 → **两者分家**。实测 **30 / 227 张非宿舍单**可见，形如「7 个只有电费没有维护费的场地块 + 1 个只有维护费的长串块」（如广联 #2661）。这是 §4 把 `splitShare` 推给 S6-2 的直接代价，T4 对账时**不要报成 bug**。宿舍侧无此问题（`splitShare` dorm 分支用 `dormRooms` key = location 原文，与唯一命中分支同源）。
